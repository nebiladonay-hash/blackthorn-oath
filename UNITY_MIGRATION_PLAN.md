# BLACKTHORN OATH — Unity migration plan

**Status:** Migration branch created; project audit underway.  
**Godot source:** `main` (preserved; do not overwrite).  
**Unity work:** `unity-migration`.  
**Unity baseline:** 6000.3.27f2 (Unity 6.3 LTS), URP, Android-first.

## Why Unity is being evaluated

The target includes lower-end Android phones. Unity offers a larger ecosystem for character animation, mobile effects, audio tooling, profiling and asset integration. It does not guarantee better performance by itself. The Unity build must prove a real advantage on target devices before it replaces the Godot build.

## Non-negotiable preservation rules

- Keep the Godot `main` branch and its history intact.
- Do not delete or rewrite Godot scenes, scripts, save data or source assets during migration.
- Port behavior deliberately; do not approximate or silently remove mechanics.
- Keep the existing player movement, three-lane runner rules, jump, slide, attack, damage, invulnerability, enemy archetypes, hazards, relic collection, kill/relic counters, run persistence, intro and menu behavior.
- Keep the existing visual assets and their source/license records. KayKit is the primary art direction where its free assets fit; do not force an unsuitable asset onto a creature or boss.
- Build and test a playable vertical slice before expanding the Unity project.
- Never call an unbuilt or untested Unity scaffold a finished migration.

## Unity architecture target

Use a clean separation between game rules and presentation:

- **Bootstrap / GameFlow:** intro, menu, run start, pause, death, restart and persistence.
- **RunnerWorld:** lane positions, forward scrolling/world movement, spawn scheduling and difficulty progression.
- **PlayerMotor:** lane transitions, jump and slide physics, collision and input buffering.
- **PlayerCombat:** attack windows, hit detection, cooldown, health and invulnerability.
- **EnemyBrain:** archetype configuration, wind-up, attack timing, damage and death.
- **Hazard / Relic:** trigger interactions with one-shot guards.
- **HUD and touch input:** compact, game-native interface; no generic dashboard panels or explanatory UI.
- **AudioDirector:** mixer groups, 3D sources, randomized footstep/impact variants, music layers and UI cues.
- **Presentation:** Animator state machines, camera follow/impulses, VFX and environment lighting. Presentation must never own core gameplay state.

Prefer Unity's Input System for touch and keyboard parity. Use a deterministic, explicit state machine for locomotion/combat. Use object pooling for repeated enemies, projectiles, particles and pickups where profiling justifies it.

## Low-end Android performance policy

Initial baseline is a stable 30 FPS target on the low tier; 60 FPS is an optional higher tier, not a promise. Use device profiling to set final targets.

- URP only; do not use HDRP.
- Start with OpenGL ES 3.0-compatible shader/material choices for the broad Android 7.1+ target supported by this Unity LTS line; verify exact device compatibility.
- Separate low, medium and high quality profiles.
- Low tier: baked lighting, one main real-time light at most, minimal/no real-time shadows, no expensive full-screen post effects, limited transparent particles, reduced render scale and conservative texture sizes.
- Avoid per-frame allocations, repeated Instantiate/Destroy in gameplay, excessive physics queries, high overdraw, many materials and unnecessary cameras.
- Use compressed textures and audio; stream long music where appropriate.
- Profile CPU, GPU, memory, thermal behavior, battery use and frame-time consistency on physical Android devices.
- Do not equate Unity's minimum runtime requirement with a practical performance target. A 1 GB device may launch but is not automatically a supported gameplay tier.

## Migration stages and exit criteria

### Stage 0 — audit (in progress)
1. Confirm source branch, source checkpoint and repository layout.
2. Map every gameplay mechanic and state transition from `main.gd` and supporting scripts.
3. Record asset formats, dimensions, animation clip names, scale, orientation and licenses.
4. Confirm which original screenshots and Android builds correspond to the source revision.

**Exit:** complete behavior map and asset manifest.

### Stage 1 — Unity foundation
1. Create a clean Unity 6.3 LTS project with URP and Android platform settings.
2. Add project structure, input, quality profiles, audio mixer and build configuration.
3. Establish reproducible CI. Android build automation requires a valid Unity Personal license activation; do not store credentials or license files in the repository.
4. Import the existing CC0 GLBs and ambient score; validate materials, scale, rig and clips.

**Exit:** Unity project opens/imports cleanly and builds an empty Android player in a licensed Unity environment.

### Stage 2 — playable vertical slice
Port one complete gameplay slice:
- player model and camera;
- lane changes, jump and slide;
- one enemy with wind-up/attack/damage/death;
- one hazard and one relic;
- attack and hit feedback;
- health, pause and restart;
- mobile touch controls;
- basic audio bus routing and footstep/sword/hit sounds.

**Exit:** the slice is playable on a physical low-end Android phone with measured frame-time and memory results.

### Stage 3 — full gameplay parity
Port all three enemy archetypes, spawning, difficulty, run progression, counters, persistence, boss presentation, intro and complete menu/HUD behavior.

**Exit:** mechanic-by-mechanic parity checklist passes.

### Stage 4 — art, UI, audio and feel
Replace placeholder/procedural presentation with a coherent KayKit-led visual language where assets fit. Build bespoke game UI, transitions, complete soundscape, animation state machine, combat feedback and atmospheric environment. No generic AI-style gradient/card interface.

**Exit:** complete first-minute experience and full run feel coherent, readable and responsive.

### Stage 5 — optimization and release QA
Test low/medium/high Android profiles, cold start, load time, thermal throttling, battery drain, memory pressure, audio latency, input latency, crashes and device-specific graphics fallbacks.

**Exit:** repeatable physical-device test report, successful Android builds and a signed release process.

## Known execution limitation

The current connected workflow can inspect and modify GitHub source, but this session does not have the Unity Editor installed or a Unity license activated. C# and project files can be prepared here; a genuine Unity import, Editor validation, Android build and performance certification require a licensed Unity Editor runner or a user-provided Unity build environment. Do not claim those tests passed until their logs/artifacts exist.

## Current decision

Proceed with the Unity migration branch as an experimental port. Keep Godot `main` as the working fallback until Unity passes the vertical-slice and physical-device gates.
